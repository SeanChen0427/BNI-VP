# 決策紀錄

## 2026-09-04｜產品版本自 v1.0.25 後改採主版、功能版、修正版

- `v1.0.0` 至 `v1.0.25` 視為早期依發布順序累加的歷史編碼，全部保留，不追溯改號。
- 從下一次實際產品發布開始：新功能增加中間的功能版號並將修正版歸零；相容的錯誤修正、安全強化或資料完整性修正只增加修正版號；不相容的世代改版才增加主版號並將後兩段歸零。
- 只有文件、測試、內部重構或部署紀錄，且不改變使用者行為時，不建立新的使用者產品版本。同一批含多種變更時採影響最高者，不按功能數量逐筆連號。
- 因此以目前 `v1.0.25` 為基準，下一批若是新功能為 `v1.1.0`、只有修正為 `v1.0.26`、不相容改版為 `v2.0.0`。
- 規則必須由共用版本核心計算，發布狀態、使用者更新紀錄第一筆與宣告的變更類型須由測試核對；總專案 `package.json` 的工具版本不等同於使用者產品版本。
- 來源：Sean 2026-09-04 指出系統已增加多項新功能但中間版號從未跳動，並確認更新版本編碼邏輯。

## 2026-09-04｜技術 CHANGELOG 採分層讀取，完整歷史與全面稽核入口保留

- `CHANGELOG.md` 繼續保存每一筆完整技術歷史，不刪除、不摘要、不移動既有內容；現行規格仍以主題文件、程式與測試為準。
- 一般開發先取得完整標題索引、最近八筆，以及以業務詞和實際程式識別名稱命中的完整條目；不得只讀搜尋命中的單行，也不得只靠近期條目判斷歷史影響。
- 權限、資料庫 migration、投票、正式資料、PALMS／計分、跨模組、回滾或搜尋後仍無法確認影響鏈時，保留完整讀取全部 CHANGELOG 的停損路徑。
- 分層工具是無網路、無寫入的本機開發輔助，不得由頁面、預覽伺服器、正式後端、分析引擎或部署入口載入。
- 來源：Sean 2026-09-04 要求先執行第一階段，前提是不影響程式作業，並須先確認風險與可節省的 token 效果。

## 2026-09-04｜委員任期只由 Admin 年度換屆流程寫入

- `committee_terms` 對所有一般登入工作階段只保留讀取權；副主席、會員委員與 Admin 均不得經瀏覽器或 Supabase REST 直接新增、修改或刪除任期。
- Admin 仍透過設定頁的年度換屆工具預覽、排定、修改或取消下一屆名單；正式寫入由 Edge API 以 `service_role` 呼叫固定 RPC，生效日由同一受保護函式原子切換。
- 正常登入姓名載入、任期判斷、投票資格及換屆待指派不變，也不增加日常操作按鈕。一般登入收權不得影響後端自動生效。
- 本次只關閉 `committee_terms` 的舊直寫路徑，不批次改寫現任或歷史任期，也不順帶修改 `people`、`members` 或其他業務資料權限。
- 來源：Sean 2026-09-04 確認內部小型系統不需企業級防護，但同意採用不增加操作負擔的最小版任期收權並直接上線。

## 2026-09-04｜全系統業務日期與畫面時間統一為台北時間

- 資料庫 `timestamptz` 與伺服器事件時間繼續以 UTC 保存，確保排序、稽核與跨系統交換不失真；只在業務判斷與畫面顯示時轉為 `Asia/Taipei`。
- 任期起訖、角色權限、年度換屆生效、截止日、排程、月度換期、檔名日期及「今天／本月」一律以台北午夜為日界，不依瀏覽器、Node 主機或資料庫工作階段時區。
- 無時區的 `datetime-local` 輸入視為台北時間；後端收到後轉成 UTC 時間戳保存，重新顯示時再轉回台北時間。
- 歷史時間戳與日期不批次改寫；本次只統一之後的解讀、判斷與顯示。BNI 計分、燈號、續約門檻與審計規則不因時區統一而改變。
- 來源：Sean 2026-09-04 確認「全系統都該是台北時間」，並要求直接修改。

## 2026-09-04｜正式委員群輸入「委員會進度」即時免費 Reply 最新工作

- 會員委員秘書Bot只在後台已核對、啟用中的正式 `committee` 群，收到完整等於「委員會進度」的文字訊息時觸發；只容許前後空白，不接受部分命中、句子夾帶、標點變體或其他一般聊天。
- 指令事件當下重新讀取 Supabase 正式未完成案件，沿用既有工作進度唯一格式，列出案件類型、會員／申請者、完整主責、完整陪訪、期限及回饋／投票階段，並以 LINE `textV2` Reply 真正 @所有人。
- Reply 訊息不計入 LINE 月訊息額度。常態通知頁原本的人工確認 Push 保留為平台異常時的備援，畫面必須明示會計入額度，不得讓使用者誤以為兩條路徑都免費。
- 系統未建立 LINE 個人身分綁定，因此正式委員群內任何成員都可輸入精確指令；安全邊界是已核對的封閉委員群，不在其他群、個人聊天室、測試群或未指定群組回覆。
- Webhook只在記憶體中比對固定指令並立即使用 `replyToken`，不保存指令全文、`replyToken` 或 LINE 使用者 ID。service-only 稽核只保存來源／回覆文案雜湊、群組目標、事件與訊息識別、時間及成敗。
- 同一 webhook 事件以唯一事件鍵防止平台重送造成重複回覆；不同時間再次輸入指令會重新取得最新資料並正常回覆，不套用「同日相同文案只發一次」的 Push 限制。
- 來源：Sean 2026-09-04 明確要求在委員群輸入特定文字（例如「委員會進度」）才即時整理發送，以便隨時呼叫並節省 LINE Push 額度。

## 2026-09-04｜年度換屆由 Admin 預排，未完成工作只在生效後集中交接

- 換屆不是日常名單逐筆編輯。設定頁提供僅系統開發人員 Admin 可見的年度工具，提前一次填入下一屆完整副主席、會員委員與未來生效日；生效前可預覽、修改或取消，正式名單與工作保持不變。
- 每屆任期固定一年。到達台北日期的生效日後，系統一次結束前屆有效任期並建立新屆任期；不刪除人員、前屆任期或歷史名單。
- 同一人留任且角色相同時，其未完成工作維持原指派。角色改變或卸任時，凡未完成工作含該人，都保留原指派快照並集中列為「換屆待指派」，由新任副主席／Admin 一次完成接手名單。
- 換屆待指派入口只在確實存在待辦時顯示；平時不在各頁堆疊一年才會使用一次的操作按鈕。
- 已結案案件不參與換屆、不可改派或刪除。必須永久保留當時主責、陪訪、結案確認人、回饋、投票資格與票向、Word 及案件歷程，以便日後回追當時負責委員。
- 現任副主席卸任後使用既有 Admin 共用帳號進行系統維護；本次功能不自動改密碼，密碼仍由 Admin 在原有帳密區另行更新。
- 來源：Sean 2026-09-04 確認一年一屆、希望提前設定而非最後一天手動處理，並要求舊有資料與當時結案委員完整可追溯。

## 2026-09-04｜已結案月會可追加「恢復續約追蹤」更正，但不得改寫草稿或原決議

- 月會尚在草稿時，可直接把續約項目從「確認不續約」切回「排定後續工作」，再補齊追蹤委員與日期。
- 月會已結案後維持整份唯讀；只有副主席／Admin 可在原本仍為「確認不續約」的續約項目使用專用更正，記錄會員後來改為續約。
- 更正採追加紀錄：原「確認不續約」決議及備註保留，另存更正原因、操作者、伺服器時間、主責、陪訪與日期，不把歷史內容覆蓋成彷彿一開始就決定續約。
- 更正必須同時建立或更新該會員的續約工作；已完成的舊工作不重新開啟，必要時建立新的更正後工作。這項操作不修改會員主檔、離會狀態、BNI 計分或燈號。
- 專用更正只能鎖定一筆已結案月會及一個續約項目；不能把已結案月會改回草稿，也不能改寫任何現有月會草稿或其他關懷項目。
- 本決策只取代 2026-08-10「正式已結案月會完全不提供排程操作」中關於續約決議反轉的極端例外；其餘已結案內容仍維持唯讀。
- 來源：Sean 2026-09-04 提出會員先婉拒、最後又決定續約的極端狀態，並明確要求實作且不得動到現有月會草稿。

## 2026-09-04｜月會確認不續約時可不建立後續工作

- 續約名單在會員委員會會中已明確確認不續約時，月會卡片可標記「確認不續約」，只保留決議及選填備註，不再強制填寫追蹤委員與排定日期。
- 結案驗證只跳過已明確標記不續約的續約項目；其他續約、紅燈關懷、期中輔導及特定關懷仍須完成分工與日期。
- 改為不續約後不會新建工作。若該會員已存在未完成工作，系統不在標記決議時自動刪除，避免一併破壞訪談、附件或案件紀錄；畫面應提醒副主席至工作總覽另行確認。
- 本標記是月會紀錄中的人工決議，不自動變更會員主檔、離會狀態、BNI 計分或燈號；正式會籍狀態仍依原流程處理。
- 來源：Sean 2026-09-04 回報實際月會中已確認會員不續約，但系統因強制建立工作排程而無法儲存結案，並明確要求可只標記不續約。

## 2026-09-04｜交流群常態提醒採 12 小時 Reply 窗口，未命中改通知 OA 全部好友

- 每週例會與月底 Key-in 都屬於前一天或更早可開始的提醒，因此開啟 12 小時機會性投遞窗口。系統設定時間為最晚送達時間，從其前 12 小時開始等待交流群的新訊息。
- 窗口內有新訊息時，副主席秘書Bot使用該事件的新 `replyToken` 立即回覆 @所有人，不儲存 token 或群聊內容。
- 12 小時未命中後，取消原設計中的交流群自動 Push 降級；改由副主席秘書Bot對該 OA 的全部可送達好友，以同一次 Broadcast 依序群發兩則訊息：先給人工貼出步驟、提醒名稱與原訂時間，再單獨給原提醒全文供長按複製。
- 不儲存副主席或管理者的個人 LINE `userId`，也不建立收件者綁定流程。目前只有副主席與管理者 2 位好友時，每次群發預計計入 2 則；日後若好友數增加，收件範圍與額度會一起增加。
- 後台管理員身分不等於 OA 好友；要收到備援通知的兩個 LINE 帳號都必須加入副主席秘書Bot好友且未封鎖。
- 備援通知只表示「已通知人工處理」，不代表交流群已收到原提醒。
- 工作台只在副主席／Admin 按下「已貼至交流群」後記為 `manual_delivered`；未確認前維持 `fallback_notified`。
- 來源：Sean 2026-09-04 確認通常提前一天或更早安排，可等待 12 小時；並明確指示未命中時不儲存個人 ID，直接由副主席秘書Bot對目前 2 位好友群發備援通知。

## 2026-08-31｜月會月份與報表月份分離，每月 1 日才切換正式儀表板

- 會員關懷儀表板的「月份」是會議／作業月份，數據固定使用上一個完整月；例如 8 月正式儀表板使用 7 月報表，9 月儀表板才使用 8 月報表。
- 月末當天允許提前上傳、對帳、AI 審視與發佈下期預備快照，但預備快照只是「已發佈・待生效」，不得在當天取代目前正式快照。
- 正式期只在台北時間每月 1 日自動切換。8 月 31 日可預備使用 8 月資料的 9 月月會快照，但直到 9 月 1 日才成為會員與 AI 查詢的正式來源。
- 上傳與分析 API 必須明確綁定報表月份；儀表板只能通過後端的正式期選擇器取值，不得由前端直接抓「日期最新」的快照。
- 歷史報表、月會與已發佈快照一律保留，新一期預備不刪除、覆寫或改寫上一期；修正顯示指標時也不得做破壞性還原。
- 來源：Sean 2026-08-31 確認「目前 8 月作業必須保持 7 月數據分析；提前提供的 8 月數據是給 9/1 會議準備，不應造成現行系統錯亂」。

## 2026-08-31｜新會員中心資料同步期

- 已由本期半年 PALMS 唯一對帳升格者立即視為正式現任會員並照 PALMS 計分。
- 若到期日／會齡報告早於升格時間且尚未收錄，缺名只列待同步資訊，不反覆彈錯、不列已到期、不推算官方會齡、續約或期中關懷時點。
- 中心來源於升格後更新即結束寬限；更新後仍缺名則恢復正式警示。
- 同步期間的個人行為解讀採新會員寬容追蹤，不把短期低分當作一般老會員退化。

## 2026-08-31｜會員關懷儀表板的細部分析由 Codex 依 BNI 分析 Skill 完成

- 本期會員關懷儀表板的細部判讀由 Codex 直接完成，不改由 Gemini、Claude 或其他外部模型代做；引擎結構化結果仍是唯一數據來源。
- 正式審視須遵守 BNI 分析 Skill：先對帳後分析，不重算分數或燈號；續約優先、紅燈深度關懷、黃燈提供可執行突破路徑、審計僅作非指控關懷線索，期中案件完成前持續跨月。
- 系統允許副主席將 Codex 的六區 Markdown 關懷報告保存至正式草稿；保存不等於發佈，仍須經副主席明確確認後才能建立不可改寫的版本化快照。
- 來源：Sean 2026-08-31 要求「關懷儀表板的細部分析由你來做」，並再次指定使用分析 Skill。

## 2026-08-31｜未完成期中關懷須跨月延續至完成

- 期中關懷仍於本次入會／復會滿 5–7 個月時到點；同一會籍週期一旦已有正式待處理或進行中任務，超過 7 個月後仍須出現在後續每月會員關懷儀表板與月會清單。
- 跨月時沿用同一正式案件，不重複建立任務；只有狀態成為 `completed` 才自後續期中關懷名單排除。重新開啟則恢復提醒。
- 舊會籍週期的未完成或完成紀錄不得帶入復會的新週期；PALMS 燈號、審計及其他數據關懷訊號仍獨立判定。
- 來源：Sean 2026-08-31 要求「這個月沒做完的期中關懷保留到下個月，以後沒做完就持續關懷直到完成」。

## 2026-08-31｜人工複製與 Bot 發送視為同一階段完成

- LINE Push 額度不足時，副主席按「複製三長群文案」後自行貼至三長群，與系統直接登記三長群完成具有相同流程效果；剪貼簿成功且 Supabase 保存成功後，立即解鎖董事顧問確認。
- 董事顧問確認同意後，副主席按「複製公告文案」並自行貼至正式公告群，與 LINE Bot 發送具有相同流程效果；複製動作保存成功後即視為公告階段完成，可進行結案。
- 人工複製與 Bot 發送共用既有 `leadersSent`／`resultAnnouncementSent` 階段門檻，但另存完成方式、操作者及時間，畫面與結案資料必須能辨識人工貼上，不得冒充 LINE OA 已送達。
- 剪貼簿操作成功不等於後端保存成功。前端須等待獨立後端動作完成才解鎖；後端仍核對副主席／Admin、正式投票決議、董事顧問狀態及最新案件 revision。
- 這項決策取代同日稍早「通過案件必須 LINE 成功送達才能結案」及「複製三長群文案只供參考」的限制。舊版未保存的複製動作不追溯猜測，須由副主席在新版重新按一次複製以建立正式紀錄。
- 來源：Sean 2026-08-31 確認實際作業已以人工複製貼至三長群及正式公告群，且 LINE 已無可用發放數，明確要求複製與 Bot 發送採相同階段效果。

## 2026-08-31｜三長群與董顧確認須在後端成功後才推進

- 續約、新會員與轉換行業別案件形成正式投票決議後，「三長群」與「董事顧問確認」必須分別由副主席明確操作，並在 Supabase 成功保存後才推進畫面階段及解鎖下一步。
- 前端不得先把 `leadersSent` 或 `advisorStatus` 當成成功再等待背景同步；同步失敗、案件版本衝突或正式前置條件不符時，維持伺服器原狀並直接顯示失敗原因。

- 本人從公開頁送出後直接寫回正式系統；若先前是副主席代填，本人可取代代填版本，已由本人送出的回饋不得再從公開頁覆蓋。送出頁提供 LINE 分享與複製，方便委員自行貼回群組延續對話，但分享與否不影響正式保存結果。
