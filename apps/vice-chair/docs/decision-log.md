## 2026-08-04｜續約雷達以中心區完成確認結束當次提醒

- 分會內的訪談、投票、董事顧問同意與案件結案不等於中心區完成續約；續約雷達繼續提醒，直到副主席／Admin 收到中心區辦公室的明確完成回覆。
- 月度分析草稿列出仍在雷達中的會員，副主席可記錄「中心已完成」及完成日。正式紀錄綁定會員與該次官方原到期日，保留確認者、確認時間與撤銷歷程。
- 確認後只排除完全相同的到期週期，不更改會員主檔的官方到期日，也不自行推算新到期日。下一份官方到期報告出現新日期時，自動視為新的續約週期。
- 誤確認可由副主席／Admin 撤銷；撤銷後原週期立即恢復續約提醒。既有已發佈分析快照保持不可改寫，新狀態於新草稿／新版本生效。

## 2026-08-04｜副主席可代填會員委員的案件回饋，但不可代投票

- 會員委員若未登入系統、而是把回饋內容貼給副主席 LINE，副主席可在案件回饋頁選擇該名委員並代為保存，不必登出後切換會員委員帳號。
- 代填回饋仍歸屬提供內容的會員委員，但系統必須另外保存實際操作的副主席，並在畫面清楚標示「由副主席代填」。
- 代填只限當期有效會員委員且必須遵守申請者迴避；副主席不得用代填功能覆蓋委員本人已提交的內容。若原內容為副主席代填，該委員之後可用本人內容取代。
- 此授權只適用於文字回饋，投票仍由每位有資格者本人操作，副主席不可代投。
- 來源：Sean 現行決策（2026-08-04）。

## 2026-08-04｜月度分析名單差異可由副主席直接確認離會

- 設定頁原有的手動離會登記與撤銷功能保留；月度分析的快捷確認僅適用於引擎已辨識出的「到期報告有、PALMS 無」差異。

## 2026-07-19｜月度分析採草稿確認工作流：未經副主席確認不得進入系統

- 月初上傳報表後，由副主席按「產出分析」啟動：引擎解析＋對帳未通過即顯示異常清單並停止，不產生草稿；通過才執行計分與 AI 審視，產出「分析草稿」。
- 分析草稿僅副主席可見；委員永遠只看得到最後一版已確認發佈的分析。系統中不存在未經確認的核心數據。
- 副主席審閱後二擇一：「確認發佈」→ 版本化快照發佈，儀表板、月會看板、續約雷達全部切換到新版；「退回重做」→ 必附退回原因，AI 帶著副主席回饋重新審視產出新草稿（重做的額外 API 呼叫為品質優先原則下可接受的成本）。
- 已發佈快照不可改寫；發現問題以重新產出新版本處理，歷史版本保留，案件與月會引用當時版本，事後更新不改寫歷史依據。
- 設計意圖：把 Sean 與 AI 在對話視窗中的迭代修正循環（審閱→回饋→修正）做進系統，並確保換屆後新副主席不存在「一鍵污染全系統」的操作可能。
- 來源：Sean 現行決策（2026-07-19）。

## 2026-07-19｜月度分析交接方案：引擎計算＋AI 審視＋人工確認（9 月換屆前完成）

- 背景：目前月度分析由 Sean 在 Claude Code 對話中依 `apps/bni-analysis/skill/SKILL.md` 執行，依賴 Sean 個人 AI 訂閱；2026-09 換屆後新任副主席無法沿用此模式。
- 定案的月度分析三段流程：
  1. **分析核心程式**（開發位置 `apps/bni-analysis`，遵守計分唯一來源原則）：自動解析報表、對帳、計分、燈號、續約雷達、審計偵測、黃燈突圍，不消耗 AI token。
  2. **AI 審視層**：以副主席個人 API Key 每月批次執行一次。負責對帳異常追因、個案綜合判讀、六區關懷報告敘事與交件前自我批判；只解讀引擎已算好的結果，不重算分數。
  3. **人工確認**：副主席過目確認後才發佈快照，維持有停點紀律。
- 個人 AI Key 用途由「制度查詢」擴充為「制度查詢＋月度分析審視」；月度審視只使用副主席本人的 Key，委員 Key 用途不變。
- 品質原則（Sean 確認）：月度審視採**完整脈絡、品質優先，不做省 token 設計**；目標是重現 Sean 與 AI 在對話視窗中的產出水準。輸入包含完整 SKILL.md 與 AGENTS.md 規格、`data/reference/` 驗證檔、離會名單、引擎本月結構化結果與上月報告。省 token 原則僅適用高頻的制度查詢。
- 對帳異常（人數不符、已到期未續約、與官方公告差異超標）為發佈前硬性擋點，沿用「對帳失敗停止輸出」原則。
- 驗收：2026-08 月度分析平行驗證——視窗照舊產出一份、引擎＋AI 審視產出一份、對照官方公告，由 Sean 判定等效才放行；2026-09 換屆前由新任副主席獨立操作一次作為交接驗收。新任副主席的 API Key 申請與綁定納入交接清單。
- 紅線沿用：AI 審視不作成資格判定、關懷語言不指控、估算標明估算。
- 來源：Sean 現行決策（2026-07-19）。

- 新系統建立於獨立專案資料夾，不干擾現有會員紅綠燈分析系統。
- 交接後的使用方式必須足夠簡單，採 SaaS 方向，不要求後任使用 Git 或建立本機開發環境。
- 第一版只設「副主席」與「會員委員」兩種日常使用角色，其他角色有需求時再追加。
- 系統另需提供管理權復原方式，但不視為第三種日常使用角色。
- LINE 公告第一版採系統產生文字及一鍵複製，由副主席確認後人工發送，不直接自動發送。
- 新會員與續約公告文字依目前提供的公版保存，未經確認不改寫。
- 名詞確認：「執事」就是「會員委員」，「執事會」就是「會員委員會」；系統介面統一使用後者，原始文件保留原文。
- 移除後台名單的案例資料不保存於專案，只保留去識別化欄位範本；健康等敏感離會原因採最小揭露原則。
- 本系統只供富聯分會使用；分會名稱固定為「富聯分會」，不設為動態欄位，也不規劃多分會切換。
- 《高屏區會員守則 V9.1》列為制度來源，版本修訂與公布日期為 2025-12-18、施行日期為 2026-01-01；與既有工具規格不一致之處先列差異，不直接改規則。
- 依 V9.1 正式用語建立「會員資格證」流程；高屏區辦公室保有最終裁量權，系統只協助檢核與送件，不自動核准。
- 續約採雙層時程管理：到期前 4 個月啟動，到期前 30 日完成全部作業；中心區辦公室保有最終審核權。原流程所稱「進階 MSP」已由下一項現行決策取代。
- 現行已無「進階 MSP」課程；續約完成公告後 8 週內，會員完成 MSP（上）或 MSP（下）任一堂即可。新會員仍須完成上、下各一次。
- 確認規範層級：使用者貼出的守則與流程文件皆為中心區規範；「到期日往前兩個月的 15 日前完成續約申請與繳費」是富聯分會內部較早的管理期限。
- 續約系統同時顯示兩層日期：富聯內部期限為主要行動截止日，中心區到期前 30 日為不可逾越的最終期限。
- 副主席與當期有效會員委員共同構成會員委員會投票基數；基數依當期名單動態計算。例如副主席 1 位加會員委員 6 位，基數為 7 位。
- 新會員、續約及一般會員委員會投票需先有超過半數基數參與，再以贊成與反對多數決；7 人基數至少 4 人投票，若 4 票為 2:2，需等待第 5 人打破平手。
- 首頁需提供副主席與會員委員的共同待辦管理；期中關懷等任務可指派 1 至 3 位會員委員，通常為 2 位，受指派者可依任務角色查看及更新資料。
- 每項關懷任務設 1 位主要負責人及 0 至 2 位陪訪人員；只有主要負責人可勾選整體完成，陪訪人員不需逐一確認。
- 新會員訪談、期中關懷、續約訪談、轉換行業別訪談及特定會員關懷的進度，對全體會員委員可見；敏感訪談內容仍依副主席與受指派人員權限控管。
- 訪談表單正式對應：終期輔導用於續約、期中輔導（GROW）用於期中關懷、高屏區會員訪談表用於新會員及轉換行業別、離會訪談表用於離會階段。
