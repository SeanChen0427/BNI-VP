# 重構路線圖

目標不是一次重寫，而是在功能持續增加時降低遺漏、除錯與 AI token 成本。

## 第 0 階段：建立地圖與護欄

狀態：本次開始執行。

- 建立 `project-manifest.json`。
- 建立 AI 開發入口、架構圖、儲存 schema 與健檢工具。
- 合併重複規格文件。
- 建立案件共用 domain 與單元測試。

## 第 1 階段：格式化與共用規則

優先級：最高，低至中風險。

1. 導入 Prettier 或 Biome，將單行 CSS／JS 正常格式化。
2. 將案件類型、表單路由、階段文案移入共用模組。
3. 將所有 storage Key 移入共用模組。
4. 將投票決議函式改成純函式並補齊測試。
5. 移除 `app.js` 等已不再使用的舊課程程式。

完成標準：相同規則只搜尋到一個定義位置。

## 第 2 階段：儲存服務與資料模型

優先級：高，中風險。

- 建立 `storage-service`，頁面不直接呼叫 localStorage。
- 定義 Case、Interview、Feedback、Vote、Attachment schema。
- 加入 schema version 與 migration。
- 將刪除案件、結案與附件清理改成 transaction 式操作。

完成標準：更換儲存方式時不用修改每一頁。

## 第 3 階段：表單共用化

優先級：中高，中風險。

- 抽出表單頁首、案件帶入、草稿保存、進度、Word 下載。
- 將重複的公司統編、委員選單、陪訪、檔名與日期函式集中。
- 正式題目與系統提示分離為資料檔。

完成標準：新增一種訪談表單不再複製整頁程式。

## 第 4 階段：正式後端

優先級：上線前必要，高風險。

- Supabase Auth 三組共用帳號（Admin／副主席／會員委員；2026-07-19 決策，不建立一人一帳號）。
- PostgreSQL 保存結構化案件。
- Private Storage 保存附件。
- Edge Functions 處理 LINE、AI、公司查詢與敏感操作。
- Row Level Security 與操作紀錄。

## 換屆前必要：BNI 分析核心與 AI 審視層（2026-09 前，與第 4 階段並行）

優先級：換屆前必要，高風險。開發位置在 `apps/bni-analysis`（計分與診斷唯一來源原則，不在工作台重寫）。

- 將 SKILL.md／AGENTS.md 的確定性規則寫成可測試的分析核心：解析、對帳、計分、燈號、續約雷達、審計偵測、黃燈突圍。
- 以 `data/reference/` 官方公告資料作回歸測試；輸出與官方逐項吻合才算通過。
- 對帳異常（人數不符、已到期未續約、與官方公告差異超標）為發佈前硬性擋點。
- AI 審視層：副主席個人 Key 每月批次一次，完整脈絡、品質優先，產出六區關懷報告初稿。
- 草稿確認工作流：產出分析→草稿（僅副主席可見）→確認發佈（版本化快照，不可改寫）或退回重做（附原因、AI 帶回饋重跑）；未經確認的分析不得進入系統任何頁面。（2026-07-19 已完成第一版：`engine/`＋`services/analysis-draft.mjs`＋`analysis-review.html`）
- 儀表板供應（2026-07-19 完成）：發佈時由 `engine/render-dashboard.mjs` 以快照重產 `index.html`（舊版自動歸檔），橋接層與 member-care.html 不需改動即取得已確認的新分析；儀表板內容自此完全由「引擎＋AI 審視＋副主席確認」供應。
- 2026-08 月度分析平行驗證；2026-09 換屆前新任副主席獨立驗收（見 `docs/decision-log.md` 2026-07-19）。

## 第 5 階段：前端框架評估

只有第 2、3 階段完成後才決定是否改 React＋Vite＋TypeScript。

不應在資料模型尚未穩定時重寫 UI，否則只會把目前混亂搬到新框架。

## 每次重構的限制

- 一次只處理一個邊界。
- 先寫相容測試，再替換消費者。
- 不混入新產品需求。
- 保留舊資料 migration，不讓現有草稿消失。
- 完成後更新 manifest、架構圖與 CHANGELOG。
